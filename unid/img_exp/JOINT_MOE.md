# 이미지 · 센서 · 분류기 동시 학습 MoE (`joint_moe.py`)

작성: 2026-11-14. 상태: 첫 실행 중 (SLURM job `48797`, 설정 `joint_moe_s_u4`). 결과는 실행이 끝나면 7절에 채운다.

## 1. 왜 만들었나

센서 모델(LightGBM)과 이미지 모델이 틀리는 곳이 다르다는 관찰에서 출발했다. 둘을 상황에 따라 골라 쓰는 MoE를 만들려고 했다. 그런데 **따로 학습한 모델을 나중에 섞는 방식**은 모두 Validation에서 이득이 없거나 손해였다.

| 방식 | 파일 | Train CV | Validation | 문제 |
|---|---|---|---|---|
| 센서 단독 (LightGBM v3+cos) | `seq_base_oof.npz` | 0.9026 | 0.9209 | 기준선 |
| CNN 확률을 LightGBM 피처로 스태킹 | `exp_stack_img.py` | 0.8996 | 0.8980 | 과적합 + 2차 누수 |
| 경계별 학습 게이트 (DINO-S 12블록, CV 1위) | `moe_gate.py` | 0.9051 | 0.9045 | CV에서는 오르고 Val에서는 떨어짐 |
| 수작업 규칙 게이트 (ConvNeXt, CV 1위) | `moe_gate.py` | 0.9046 | 0.9210 | 효과 없음 (Val Δ 95% CI ±0.008) |
| 센서 logit 고정 + DINO 보정 공동학습 | `finetune_dino.py --sensor_residual` | 0.8876 | 0.8754 | 학습 실험의 센서 오류 패턴을 외움 |

실패 원인은 두 가지로 정리된다.

1. **학습과 추론에서 센서 수준이 다르다.** 게이트·잔차 모델은 센서 **OOF** 확률(해당 실험을 안 본 약한 모델)로 학습한다. Validation/Test에는 Train 전체로 학습한 더 정확한 센서가 들어간다. 그래서 이미지를 과하게 섞는다.
2. **사후에 섞으면 두 모델의 오류가 갈리지 않는다.** L2/L3 경계에서 ConvNeXt 이미지 모델은 센서 오답 1,324건 중 529건을 맞히지만, 센서가 맞은 프레임 616건을 틀린다. 게이트 입력(센서 확신도, 경과 시간, 이미지 변화량)으로는 이 둘을 구분하지 못한다.

`joint_moe.py`는 두 문제를 구조적으로 없앤다. **센서 인코더, 이미지 인코더, 게이트, 분류 헤드를 하나의 모델로 만들고 하나의 손실로 함께 학습한다.** 한 모델이 OOF와 Validation/Test 출력을 모두 내므로 스태킹 단계가 없고, 분포 차이도 생기지 않는다.

LightGBM은 트리 분할이 미분되지 않아 gradient를 받을 수 없다. 그래서 센서 쪽은 **같은 센서 피처를 입력으로 받는 MLP**로 바꿨다.

## 2. 구조

```
현재 프레임 ─┐                         ┌─ CLS_cur ─┐
             ├─ DINOv2-S (가중치 공유) ─┤  patch_mean_cur ├─ LayerNorm → Dropout → Linear → GELU ─→ z_img (256)
30초 전 프레임┘   마지막 4블록만 학습   └─ CLS_cur − CLS_prev ┘

센서 피처 735 + 결측 표시 292 ─→ MLP (1027 → 512 → 256) ─────────────────────→ z_sen (256)

z_sen ──────────────→ 센서 헤드  Linear(256→5)        = S
z_img ──────────────→ 이미지 헤드 Linear(256→5)        = I
[z_sen, z_img] ─────→ 결합 헤드  MLP(512→256→5)       = J
[z_sen, z_img] ─────→ 게이트     MLP(512→64→15) → 경계별 softmax over {S, I, J}  = w (5 경계 × 3 전문가)

출력 logit P(y ≥ k) = w_S,k · S_k + w_I,k · I_k + w_J,k · J_k ,  k = 2..6
```

- **출력은 순서형(ordinal)이다.** 6개 클래스 대신 경계 5개의 누적확률 P(y≥2), …, P(y≥6)을 낸다. 단계가 앞으로만 진행된다는 구조를 반영한다. 클래스 확률은 누적확률을 단조 보정(누적 최솟값)한 뒤 차분해서 얻는다.
- **게이트는 경계마다 따로 정해진다.** 예를 들어 L2/L3 경계에서는 이미지를, L4/L5 경계에서는 센서를 믿는 식의 조합을 학습할 수 있다.
- **전문가는 3개다.** 센서 단독, 이미지 단독, 그리고 두 표현을 함께 보는 결합 헤드다. 결합 헤드는 "센서가 이런 상태일 때 이미지가 이렇게 보이면" 같은 상호작용을 맡는다.

## 3. 입력

### 이미지

| 항목 | 내용 |
|---|---|
| 백본 | `facebook/dinov2-small` (ViT-S/14, 22M, Apache-2.0). HF 캐시 `hf_cache/` |
| 프레임 | 현재 프레임 + 같은 실험의 30초 전 프레임. 30초 전이 없으면 첫 프레임. 과거만 사용 |
| 크기·정규화 | 224×224, 두 프레임 모두 ImageNet 평균/표준편차로 정규화 |
| 증강 (학습만) | 두 프레임에 같은 random crop(0.85~1.0)과 좌우 뒤집기. 색 변형 없음 (열화상 색 = 온도) |
| 캐시 | 전 프레임 47,173장을 224 uint8로 RAM에 올림 (약 7.1GB) |

### 센서

| 항목 | 내용 |
|---|---|
| 피처 | `val0.9195/features.py`의 `build_features` 735개 (LightGBM 기준 모델과 같음, 인과적·초 단위 윈도우). 이미지 코사인 피처 9개는 이미지 인코더가 대신하므로 뺐다 |
| 변환 | 부호 보존 log 압축 `sign(x)·log1p(|x|)` → 표준화 → ±5로 클리핑 |
| 결측 | 결측을 0으로 채우고, Train fold에서 결측이 있는 열(약 292개)마다 결측 표시 열을 추가한다. "아직 그 온도를 넘지 않음" 같은 결측 자체가 정보라서다 |
| 누수 방지 | 평균·표준편차·결측 열 목록은 **fold의 학습 실험으로만** 계산하고 체크포인트에 저장한다 |

## 4. 학습

| 항목 | 값 |
|---|---|
| 손실 | BCE(MoE 출력) + 0.3 × [BCE(센서 헤드) + BCE(이미지 헤드)] |
| 보조 손실 이유 | 한쪽 전문가만 쓰고 다른 쪽은 학습되지 않는 현상(MoE의 전문가 붕괴)을 막는다 |
| 경계별 양성 가중치 | √((1−p)/p), p = 해당 경계 양성 비율. 희소한 상위 단계(≥5, ≥6) 경계 보정 |
| label smoothing | 0.05 |
| 최적화 | AdamW (weight decay 0.05), OneCycle (warmup 15%, cosine), grad clip 2.0, bf16 AMP |
| 학습률 | 센서 MLP·헤드·게이트 1e-3 / DINO 마지막 블록 3e-5, 앞 블록으로 갈수록 0.8배씩 감소 |
| 에폭 | 10 |
| 배치 | 64 (이미지는 현재+과거 2장이라 백본에는 128장이 들어감) |
| 샘플링 | 에폭마다 실험별 최대 200프레임을 무작위로 뽑음. 거의 같은 연속 프레임을 반복 학습하지 않도록 |

## 5. 검증과 출력

- **CV**: Train 78개 실험 GroupKFold(5, shuffle, seed 0). 다른 실험들(`finetune.py`, `seq_experiments.py`)과 같은 분할이다.
- **평가 조건**: fold 검증과 Validation 모두 Test처럼 실험당 500행으로 캡하고, 확신 cummax(τ=0.7) 후처리 후 Macro F1을 잰다.
- **Validation / Test**: 5개 fold 모델 출력의 평균. Test는 주어진 데이터를 그대로 넣고 추론에만 쓴다.
- **로그** (`logs/joint_moe_s_u4.log`):
  - 에폭마다: fold F1(MoE / 센서 헤드 단독 / 이미지 헤드 단독), 게이트 평균 가중치 (센서, 이미지, 결합), 에폭 시간, 최대 GPU 메모리
  - 마지막에: Train CV와 Validation을 같은 세 항목으로 출력
- **출력 파일**:
  - `joint_moe_s_u4.npz`: `sample_id`, `split`, `probs`(n×6), `cum`(MoE 누적확률 n×5), `cum_s`, `cum_i`(전문가별 누적확률), `w`(전문가별 평균 게이트 가중치 n×3). Train은 OOF, Validation·Test는 5-fold 평균
  - `joint_moe_s_u4_models/fold_*.pt`: fold별 가중치와 센서 전처리 통계

## 7. 판단 기준과 예상 위험

**채택 조건**: MoE 출력이 LightGBM 센서 단독(CV 0.9026 / Val 0.9209)보다 Train CV에서 나아야 하고, Validation에서도 떨어지지 않아야 한다. Validation 변화는 실험 단위 bootstrap 신뢰구간으로 본다(`moe_gate.boot_diff`).

**예상 위험**

1. **센서 MLP가 LightGBM보다 약할 수 있다.** 표형 피처에서는 보통 GBM이 MLP보다 강하다. 로그의 "센서 헤드 단독" 점수가 그 손해 크기다. 이 손해가 이미지 보완 이득보다 크면 MoE는 LightGBM을 넘지 못한다.
2. **실험 수가 적어 과적합할 수 있다.** 잔차 공동학습이 Train CV에서도 떨어진 원인이 학습 실험의 오류 패턴 암기였다. 이 모델도 자유도가 크므로 fold F1이 에폭 후반에 떨어지는지 본다.
3. **게이트가 한쪽으로 쏠릴 수 있다.** 게이트 가중치가 센서 쪽으로만 쏠리면 사실상 센서 MLP 단독 모델이다.

**결과** (2026-11-14, `joint_moe_s_u4`, 224×224 강제 리사이즈, fold 병렬 job 48798~48801)

| | Train CV | Validation |
|---|---|---|
| LightGBM 센서 단독 | **0.9026** | **0.9209** |
| MoE 출력 | 0.8915 | 0.8813 |
| 센서 헤드 단독 (MLP) | 0.8623 | 0.8918 |
| 이미지 헤드 단독 | 0.7931 | 0.7750 |
| 게이트 평균 가중치 (센서, 이미지, 결합) | 0.16, 0.34, 0.50 | 0.16, 0.33, 0.51 |

fold별 (MoE / 센서 MLP / 이미지 / 같은 fold LightGBM):

| fold | MoE | 센서 MLP | 이미지 | LightGBM |
|---|---|---|---|---|
| 0 | 0.9033 | 0.8900 | 0.8085 | 0.9295 |
| 1 | 0.9118 | 0.8676 | 0.8067 | 0.9221 |
| 2 | 0.8387 | 0.8379 | 0.6673 | 0.8391 |
| 3 | 0.8784 | 0.8602 | 0.7536 | 0.8991 |
| 4 | 0.8979 | 0.8427 | 0.8399 | 0.9000 |

해석:
- **채택 조건 미달.** MoE가 LightGBM보다 Train CV −0.011, Validation −0.040 낮다. 5개 fold 모두 LightGBM 이하다.
- **Train CV에서는 이미지가 보탠다.** MoE가 센서 MLP 단독보다 +0.029 높다. 그러나 센서 MLP 자체가 LightGBM보다 0.040 낮아서(위험 1) 그 손해를 메우지 못한다.
- **Validation에서는 이미지가 오히려 깎는다.** MoE(0.8813)가 센서 MLP 단독(0.8918)보다 낮다. 특히 L4(0.825), L5(0.859)에서 손해가 크다.
- 최대 GPU 메모리 5.7GiB (batch 64). fold 2개 기준 약 7분 (RTX 6000 Ada).
- 알려진 한계: 이미지 크기가 36×76~336×297로 크게 다른데 전부 224×224로 늘렸다. 작은 세로형 이미지(Train 26개 실험)에서 이미지 모델 F1이 0.06~0.08 낮다.

## 7-1. v2 (`joint_moe2.py`): 센서 트랜스포머 디코더 + 비율 유지 이미지 + 20 에폭

바뀐 점: 센서 인코더를 MLP에서 인과적 트랜스포머 디코더(같은 실험의 과거 64행, 3층·4헤드, Δt 인코딩)로 교체했다. 이미지는 원본 비율을 유지하고, 짧은 변 ≥112px·긴 변 ≤336px·14의 배수로 맞추며 최근접 보간을 쓴다. 같은 크기끼리 배치를 묶고, 원본 크기·비율을 게이트 입력에 넣었다. 에폭은 10 → 20, GPU 메모리는 15GB로 제한했다. 실험 하나에 크기가 섞여 있어서 목표 크기는 실험별로 하나(가장 흔한 원본 크기 기준)로 정했다.

| v2 게이트 평균 가중치 (센서, 이미지, 결합) | 0.41, 0.34, 0.25 | 0.40, 0.34, 0.26 |

이미지 크기 그룹별 이미지 헤드 단독 F1 (Train OOF):

| | 큰 이미지 (52개 실험) | 작은 세로형 (26개 실험) |
|---|---|---|
| v1 (224×224 강제) | 0.803 | 0.706 |
| v2 (비율 유지) | 0.795 | 0.718 |

해석:
- **v2도 LightGBM을 넘지 못했다.** v1과 비교하면 CV −0.002, Val −0.004로 사실상 같다.
- **비율 유지 처리의 효과는 작다.** 작은 이미지에서 +0.012, 큰 이미지에서 −0.008이다. 작은 이미지에서 성능이 낮은 원인은 리사이즈 방식보다 이미지 자체의 정보량(작은 크롭)으로 보인다.
- **센서 트랜스포머는 CV와 Val이 엇갈린다.** MLP보다 CV는 낮고(0.845 vs 0.862) Val은 높다(0.905 vs 0.892). 실험 수가 적어 둘 중 어느 쪽이 나은지 판단할 수 없다.
- **Validation에서는 여전히 섞으면 손해다.** v2 MoE(0.877)가 자신의 센서 헤드 단독(0.905)보다 0.028 낮다. v1과 같은 패턴이다.
- **에폭마다 점수가 크게 흔들린다.** fold 0의 MoE가 2에폭 간격으로 0.81~0.92를 오간다. 확신 cummax 후처리에서 한 번 잘못 확신하면 그 뒤가 전부 틀리기 때문으로 보인다. 그래서 마지막 에폭 하나로 낸 fold 점수는 잡음이 크다.
- GPU 메모리 최대 11.9GiB (15GB 한도 안). RTX 5080 16GB를 혼자 쓰면 돌아간다.
